## R2. Playwright for .NET: package and browser install on ubuntu-latest

- Package `Microsoft.Playwright` (NuGet). On build, the package's MSBuild targets copy the driver and generate `bin/<Configuration>/<TFM>/playwright.ps1` (this is the documented install path for .NET). Browsers are installed with `pwsh bin/Release/net10.0/playwright.ps1 install --with-deps chromium`. `pwsh` is preinstalled on GitHub's `ubuntu-latest` runner image, so no `setup-powershell` step is needed; `--with-deps` runs `apt-get` (the runner user has passwordless sudo, Playwright calls it itself). `npx playwright install` is NOT used: it would need Node and would install a Playwright-node browser revision that may not match the .NET library's expected revision; the generated script always installs the exact revision the pinned .NET package wants.
- Alternative `dotnet tool install --global Microsoft.Playwright.CLI` exists but is the older route and adds another version to pin; rejected.
- The install must run after `dotnet build` of the E2E project (the script is a build output). Browser cache: `~/.cache/ms-playwright`; optional `actions/cache` keyed by the Playwright version saves ~100 MB download but `--with-deps` still runs apt; skipped for simplicity (Known Gap candidate).
- Local first run: `pwsh CategoryProduct.E2ETests/bin/Debug/net10.0/playwright.ps1 install chromium` (Windows PowerShell 5.1 also works with `powershell` for that script on Windows when `pwsh` is missing; documented in quickstart).
- Version: pin the newest stable version at least two weeks old, verified with `dotnet package search Microsoft.Playwright --exact-match --format json` (or the NuGet page) at implementation time; recorded in Known Gaps. The workflow header comments name the version so a bump touches both the csproj and nothing else.

## R3. Skip vs fail

xunit v2 has no runtime skip, so the skip is static: `E2EFactAttribute` sets `Skip` in its constructor from the environment (`Environment.GetEnvironmentVariable("E2E_BASE_URL")`). That gives the required behavior: locally without Docker nothing runs and nothing fails. When the variable IS set, the user asked for a real run: unreachable stack, missing admin variables or a login failure fail loudly with one clear message from the fixture (a skip there would let CI go green with zero coverage). The attribute lives in the test assembly, so the skip message is visible in `dotnet test` output.

## R4. Test framework choice

`Microsoft.Playwright.Xunit` (a separate package) targets xunit v2 and offers `PageTest`, but it controls browser/context lifecycle itself, uses `PLAYWRIGHT` env settings for options, and gives no hook for failure screenshots/traces in xunit v2. A small custom base (about 80 lines) gives: env-based skip, one browser per run, fixed locale/time zone, failure artifacts, and no extra package to pin. Chosen: library + custom base. NUnit's `PageTest` has built-in trace-on-failure but would introduce a second test framework to a repo that uses xunit everywhere.

## R5. CI placement: new job `e2e`, independent of `compose-smoke`

Options: (a) extend `compose-smoke`; (b) new job `e2e` after `docker-build`; (c) new job fully independent.
- (a) couples two concerns: smoke asserts "the stack boots" with curl in a few minutes; E2E needs the SDK, a browser install (about 1-2 min with deps), a different timeout, artifacts, and a different set of env (bootstrap admin, rate-limit override). A broken E2E would hide as a "smoke" failure, and the smoke job would stop being a fast signal.
- (c) wastes runner minutes when a Dockerfile is broken (the same `docker build` would fail twice).
- (b) chosen: `needs: docker-build` (the two `docker build` commands are the cheapest gate and fail first); runs in parallel with `compose-smoke` and `sqlserver-tests`; builds the stack again with `docker compose up --build` (cache is not shared between jobs; accepted). It does not need `build-test`: unit/integration failures should not block seeing E2E results. Different host ports are unnecessary because jobs run on separate runners; the same `5256`/`5028` are used for consistency with `compose-smoke`.
- Timeout: 25 minutes (build ~5-8 min, browser install ~2 min, tests ~5 min).

## R6. Admin seeding and secrets in CI

Same random-`.env` approach as `compose-smoke`, plus `BOOTSTRAP_ADMIN_USERNAME="e2e-admin-$(openssl rand -hex 4)"` (random suffix; only the password is secret) and `BOOTSTRAP_ADMIN_PASSWORD="E2e-$(openssl rand -hex 12)-Aa1"`. The password is masked and exported to the later step through `$GITHUB_ENV` (masked values stay masked in logs) as `E2E_ADMIN_USERNAME` / `E2E_ADMIN_PASSWORD`; `E2E_BASE_URL=http://localhost:5256`. The database starts empty each run (`down -v` at the end and a fresh runner), so the bootstrap runs. The `.env` is in the repository root, which is not an artifact path; the artifact uploads `CategoryProduct.E2ETests/bin/Release/net10.0/test-results/` only (the working directory of the tests; `E2E_RESULTS_DIR` is set to an absolute `${{ github.workspace }}/test-results` to remove ambiguity, and that exact path is uploaded).

## R7. Rate limit override

Raising limits needs `RateLimiting__LoginPermitLimit` etc. on the `api` container. Options: edit `docker-compose.yml` to pass through variables (`${RATE_LIMIT_LOGIN:-5}`) - changes the shipped compose and `compose-smoke` unaffected but still a production-file edit; or an additive override file used only by E2E (`docker compose -f docker-compose.yml -f docker-compose.e2e.yml up`). Chosen: override file, value `1000`, six keys (login, register, forgot-password, password, logout, profile; `refresh` already 30 and used only on token expiry). The override file contains no secrets. Compose merges `environment` maps from both files.

## R8. Stability rules

Web-first assertions only (`Expect(locator).ToBeVisibleAsync()`, `ToHaveTextAsync`, `ToHaveURLAsync`), actions auto-wait for actionability; navigation by `page.GotoAsync` or by clicking and then asserting the destination (never read the DOM immediately after a click). No `WaitForTimeoutAsync`, `Task.Delay`, `Thread.Sleep` (grep gate T029). Timeouts: `SetDefaultTimeout(15_000)`, `SetDefaultNavigationTimeout(30_000)`, `Expect` timeout 15 s (`Assertions.SetDefaultExpectTimeout`), per-test xunit timeout is not available in v2, the whole step has a job `timeout-minutes`. Retries: none, no `--retries`, no re-run action. Test data unique per test, tests order-independent, classes sequential. Locale and time zone fixed. Each test performs its own sign-in so a logout in one test cannot invalidate another test's session. Use `WaitUntil = DOMContentLoaded` default for navigations (pages are server-rendered).

## R9. Failure artifacts

`BrowserTestBase.RunAsync` wraps each test: `context.Tracing.StartAsync(new() { Screenshots = true, Snapshots = true, Sources = false })` before; on exception `page.ScreenshotAsync(FullPage)`, `context.Tracing.StopAsync(new() { Path = ... })`, and a `.txt` with URL, console messages (collected by `page.Console`), failed requests (`page.RequestFailed`) and HTTP status >= 500 responses (`page.Response`), then rethrow so xunit reports the original failure; on success `Tracing.StopAsync()` with no path. File names `<Class>.<Method>`. Traces can contain typed form values; only throwaway data exists (random passwords of throwaway users, the throwaway Admin of a throwaway stack), retention is 7 days, and the upload is `if: failure()` only. The text file never includes cookie values or request bodies. View a trace with `pwsh .../playwright.ps1 show-trace <zip>` (quickstart).

## R10. Why these scenarios and what is deliberately left out

Chosen because each needs a browser: client-side validation without a request (jQuery Validate), real cookie flags, real file upload and image decode, SVG render, anti-forgery POST flows through the real stack, role redirects with real cookies. Left out: password reset by email (A6), real unhandled-exception page (needs a test-only endpoint), `Remove image`, pagination, search/sort (covered by MVC tests, no JS involved), Users admin page (no JS), profile/change password (covered by 025 MVC tests; the JS validation partial is already exercised on Register).

## R11. Local developer workflow

Docker is required for a real run (the dev machine of this repository has none; CI is the verification). With Docker: `docker compose -f docker-compose.yml -f docker-compose.e2e.yml up -d --build` with a `.env` containing `SA_PASSWORD`, `JWT_KEY`, `BOOTSTRAP_ADMIN_USERNAME`, `BOOTSTRAP_ADMIN_PASSWORD`; then `E2E_BASE_URL=http://localhost:5256`, `E2E_ADMIN_USERNAME`, `E2E_ADMIN_PASSWORD` and `dotnet test CategoryProduct.E2ETests`. Without Docker the project builds and every test is skipped.
